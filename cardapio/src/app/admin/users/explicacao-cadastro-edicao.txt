================================================================================
CADASTRO E EDICAO DE USUARIOS — O QUE FOI FEITO E POR QUE
================================================================================

Objetivo
--------
Criar uma unica tela para cadastrar e editar usuarios no painel admin.

- Botao "Novo"  -> cadastro (sem ID)
- Clique na linha da tabela -> a mesma tela, com o ID na URL, buscando
  os dados no banco para preencher o formulario

Campos: nome, e-mail, usuario, display, papel (role), status e senha
(obrigatoria no cadastro; opcional na edicao).


================================================================================
1. NAVEGACAO (lista + mesma tela com ou sem ID)
================================================================================

Arquivos:
  src/app/admin/users/page.tsx
  src/app/admin/users/page.module.css

O que mudou na lista
--------------------
- Botao "Novo" apontando para /admin/users/form
- Cada linha da tabela abre /admin/users/form?id=<uuid>
- O filtro que mostrava so usuarios "active" foi removido

Por que
-------
O pedido era uma unica tela, diferenciada pelo parametro ID. Query string
(?id=) atende isso sem precisar de duas rotas (/new e /[id]).

A linha inteira e clicavel com um link "esticado" na primeira celula
(classe stretchedLink). Nao da para envolver <tr> com <a> (HTML invalido),
entao o ::after do link cobre a linha.

O filtro de ativos foi tirado porque, se da para inativar um usuario no
formulario, ele precisa continuar visivel na lista para ser editado de
novo (reativar, corrigir dados, etc.).

Papeis e status na tabela aparecem em portugues (Administrador, Gerente,
Ativo, Inativo) so na exibicao. No banco continuam admin/manager e
active/inactive.


================================================================================
2. TELA DO FORMULARIO
================================================================================

Arquivos:
  src/app/admin/users/form/page.tsx          (Server Component)
  src/app/admin/users/form/UserForm.tsx      (Client Component)
  src/app/admin/users/form/page.module.css

Como a mesma tela serve para os dois casos
------------------------------------------
page.tsx e um Server Component. Ele le searchParams.id:

- Sem id  -> cadastro. Titulo "Novo usuario". Formulario vazio.
- Com id  -> edicao. Busca o usuario via UserService.findById().
             Se nao existir, notFound(). Titulo "Editar usuario".
             Passa os dados ja prontos para o UserForm (sem senha).

Por que o form e Client Component
---------------------------------
Estado dos campos, submit com fetch, mensagens de erro e o campo senha
precisam rodar no browser. O page.tsx continua no servidor para buscar
o usuario no banco sem uma chamada HTTP extra (mesmo espirito da lista).


Campos e regras da UI
---------------------
- Nome, e-mail, usuario, display, papel, status, senha
- E-mail entra no formulario porque o banco exige e-mail unico
  (Better Auth / tabela user), mesmo o login sendo por username
- Senha obrigatoria no cadastro (minimo 6 caracteres, alinhado ao seed)
- Na edicao, senha em branco = nao altera a senha atual
- Display vazio: o service grava o proprio username (igual ao seed)
- Cancelar volta para /admin/users
- Salvar chama POST /api/users (novo) ou PATCH /api/users/[id] (edicao)

O botao voltar do header do admin continua indo para /admin. Isso ficou
de fora de proposito: o Cancelar do formulario cobre o retorno a lista.

Visual
------
Card branco, inputs e botao amarelo no mesmo padrao da tela de login
(tokens --mamute-*).


================================================================================
3. POR QUE NAO USAR O BETTER AUTH PARA CRIAR USUARIO
================================================================================

O auth esta em src/lib/auth.ts com:

- emailAndPassword.disableSignUp: true  -> nao existe cadastro publico
- role e status com input: false        -> o client do Better Auth nao
                                           pode gravar esses campos

Por isso o cadastro admin NAO usa authClient.signUp. Segue o mesmo
caminho do script scripts/seed-admin.ts:

1. Gera um UUID
2. Insere na tabela user (dados + role + status)
3. Insere na tabela account (providerId = "credential")
4. A senha vai hashed com hashPassword de better-auth/crypto

A senha NUNCA fica na tabela user. Fica em account.password, que e o
que o Better Auth usa no login por usuario/senha.

Se a senha fosse gravada de outro jeito, o login quebraria.


================================================================================
4. ARQUITETURA (Zod -> API -> Service -> Repository)
================================================================================

O README do projeto define esse fluxo para a area administrativa.
Os arquivos ja existiam como stub (TODO). Foram preenchidos.

4.1 Validacao — src/validations/user.validation.ts
--------------------------------------------------
createUserSchema: senha obrigatoria
updateUserSchema: senha opcional; se vier preenchida, minimo 6 caracteres

Nao usamos createUserSchema.partial() no update. Partial deixaria nome,
e-mail, role etc. opcionais, e o formulario envia o registro inteiro.

E-mail e normalizado (trim + lowercase). Username no service tambem vai
para lowercase, como no seed, para o login nao depender de maiusculas.

4.2 Repository — src/repositories/user.repository.ts
----------------------------------------------------
Unica camada que fala com o Drizzle nesta feature (alem da lista, que
ainda consulta o banco direto, como ja fazia).

Metodos:
  findById, findByUsername, findByEmail
  create  -> user + account
  update  -> campos do user; se vier passwordHash, atualiza account
             (ou cria o account credential se ainda nao existir)

toUser() devolve o tipo User da aplicacao, sem hash de senha.

4.3 Service — src/services/user.service.ts
------------------------------------------
Regras de negocio:

- Unicidade de username e e-mail (409 se ja existir)
- Na edicao, ignora o proprio ID na checagem de unicidade
- Username e e-mail em lowercase
- Display vazio vira o username digitado
- Hash da senha (create sempre; update so se o campo veio preenchido)
- UserServiceError com status HTTP (404, 409) para a API traduzir

4.4 APIs
--------
  POST  /api/users        src/app/api/users/route.ts
  PATCH /api/users/[id]   src/app/api/users/[id]/route.ts

GET /api/users continua 501 (listar pela API nao era o escopo; a lista
ja carrega no Server Component).

As rotas /api/* NAO passam pelo middleware que protege /admin. Por isso
cada handler chama requireAuth() (src/middleware/auth.ts). Sem isso,
qualquer um poderia criar/editar usuario batendo na API.

Fluxo do POST/PATCH:
  1. requireAuth()
  2. Zod (400 se invalido)
  3. UserService
  4. JSON de resposta (201 no create)

A tela de edicao NAO usa GET /api/users/[id]. O page.tsx busca no
servidor via UserService.findById, sem round-trip HTTP.
